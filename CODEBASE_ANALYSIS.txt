SECTION 1 — WHAT THE APP IS
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Syntra is an offline-first Flutter app for building social confidence through
deliberate social challenges. Users are presented with real-world social tasks
(e.g. "start a conversation with a stranger", "give someone a compliment"),
accept them with a countdown timer, and log whether they succeeded or not.
XP ("Aura Points") is awarded on success, streaks are tracked, and every
attempt is stored in a logbook.

The app is structured around a progression system: a five-level Comfort Zone
Level (CZL) which gates which challenges are visible, unlocking harder content
as the user completes enough challenges at their current level.

Each day a Mission Board offers three tailored challenges (Comfort / Growth /
Bold tier), with a 10% XP bonus for completing daily missions. The app reminds
users via local notifications and celebrates streaks with an animated screen.

There is no backend, no account system, and no cloud sync. All data lives on
the device.

TECH STACK:
  Flutter (Dart) · Riverpod 2.x · go_router · SQLite (sqflite) ·
  SharedPreferences · flutter_local_notifications · fl_chart ·
  audioplayers · vibration · intl (flutter_intl)

PLATFORM SUPPORT:
  Android — fully supported, including exact-alarm scheduling via AlarmManager
  iOS — supported with flutter_local_notifications (UNUserNotificationCenter);
        no native scheduling layer equivalent to Android exists

APP VERSION: 1.0.0+1 (pre-release)
DART SDK: ^3.8.1

─── 3.1 APP STARTUP ────────────────────────────────────────────────────────────

main() runs these steps synchronously before runApp():

  1. WidgetsFlutterBinding.ensureInitialized()
  2. tz.initializeTimeZones() — timezone data for notification scheduling
  3. _copyDatabaseIfNeeded() — copies challenge_database.db from assets to the
     sqflite database directory if not already present (first launch only).
     NOTE: this DB now only stores the logbook table; the challenge catalog
     has moved to JSON.
  4. _migrateSettingsJson() — one-time migration: reads the legacy settings.json
     from documents dir, writes all values to SharedPreferences via
     SettingsRepository, then deletes the JSON file. Best-effort (errors ignored).
  5. SettingsRepository.instance.loadOnboardingComplete() — read before router
     init so the router can set initialLocation correctly without async redirect.
  6. routerNotifier = RouterNotifier(onboardingDone) — global late final ChangeNotifier
     used by GoRouter's refreshListenable.
  7. SyntraNotificationService.instance.initialize() — Flutter plugin init +
     Android MethodChannel setup.
  8. runApp(ProviderScope(child: SyntraApp()))

SyntraApp (ConsumerWidget):
  - Watches themeModeProvider → ThemeMode (light/dark/system)
  - Watches localeProvider → Locale (en/de)
  - Renders MaterialApp.router with AppTheme.light(), AppTheme.dark(),
    appRouter (GoRouter), S.delegate for localization.


─── 3.2 NAVIGATION ─────────────────────────────────────────────────────────────

Router: go_router (GoRouter) with a ChangeNotifier-based refresh.

ROUTE GUARD (router.dart):
  GoRouter.redirect checks routerNotifier.onboardingComplete:
    - Not done + not on /onboarding → redirect to /onboarding
    - Done + on /onboarding → redirect to /
    - Otherwise → null (no redirect)

NAMED ROUTES (AppRoutes abstract class):
  /                    → HomeBar (bottom-nav shell)
  /onboarding          → OnboardingScreen
  /active_challenge    → ActiveChallengeScreen (extra: Challenge)
  /challenge_done      → ChallengeDoneScreen (extra: _ChallengeDoneArgs)
  /logbook             → LogbookPage
  /logbook_detail      → LogbookDetailPage (extra: Map<String,dynamic>)
  /about               → AboutNotePage
  /streak_celebration  → StreakCelebrationScreen (extra: _StreakCelebrationArgs)

EXTENSION HELPERS (AppNavigation on BuildContext):
  context.goActiveChallenge(challenge)
  context.goChallengeDone(challenge, rewardFactor)
  context.goLogbook()
  context.goLogbookDetail(entry)
  context.goAbout()
  context.goStreakCelebration(streak, isMilestone)

BOTTOM NAVIGATION (HomeBar):
  Uses a PageView + NavigationBar. Tabs:
    0 — ChallengesScreen    (explore icon)
    1 — DailyChallengeScreen (calendar icon)
    2 — StatisticsScreen    (bar_chart icon)
    3 — SettingsScreen      (settings icon)

  PageView is swipeable (BouncingScrollPhysics) so users can swipe between tabs.
  Programmatic tab switches use homeTabIndexProvider (StateProvider<int>).
  HomeBar listens to homeTabIndexProvider and calls animateToPage().

NOTEWORTHY INCONSISTENCY:
  ActiveChallengeScreen pushes ChallengeDoneScreen with Navigator.of(context).push<double>
  (old-style navigator), not GoRouter. This is intentional (it needs a return value)
  but means /challenge_done is not reachable via deep link from this path.

─── 3.4 CHALLENGE DATA LAYER ────────────────────────────────────────────────────

CATALOG (read-only, JSON):

  ChallengeRepository (lib/data/challenge_repository.dart)
  Pattern: Singleton, in-memory cache per language

  loadChallenges(languageCode) → Future<List<Challenge>>:
  1. Returns cached list if language matches.
  2. Loads assets/data/challenges.json (metadata: id, xp, timer, type, flirt,
     frequency, environment).
  3. Loads assets/data/translations/{languageCode}.json (title, description, hint).
  4. Falls back to 'en' translations if a key is missing in the requested language.
  5. Builds List<Challenge> and stores in _cache.

  invalidate() clears the cache (e.g., on language switch).

LOGBOOK (read/write, SQLite):

  LogbookRepository (lib/data/logbook_repository.dart)
  Pattern: Singleton, lazy database open

  Database: challenge_database.db (same file as original, but only the logbook
  table is used — challenge tables in the file are ignored)

  Schema version 2 (via onUpgrade migration):
    logbook table:
      id               INTEGER PK AUTOINCREMENT
      challenge_id     INTEGER (stored as integer, coerced to string on read)
      status           TEXT     'success' | 'tried'  (NOTE: 'tried', not 'failed')
      earned           INTEGER  XP awarded (0 for aborted)
      timestamp        DATETIME ISO8601 string
      notes            TEXT     nullable
      feeling          INTEGER  nullable, 0–4 emoji scale
      perception       INTEGER  nullable, 0–4 emoji scale
      duration_seconds INTEGER  nullable (added in v2 migration)

  Key methods:
    addEntry(...)                   → INSERT
    allEntries({limit, offset})     → paginated SELECT DESC
    entryById(id)                   → SELECT by PK
    overviewStats()                 → single-query aggregate:
                                       totalXp, todayXp, completedAllTime,
                                       completedToday, streak, minutesBrave
    weeklyXp({days=7})              → List<int> XP per day (oldest→newest)
    weeklyChallengeCounts({days=7}) → List<List<int>> [successes, tried] per day
    activityHeatmap({weeks=12})     → Map<dateStr, count> for heatmap grid
    completedChallengeIds()         → Set<String> of all success challenge_ids
    lastNotesForChallenge(id)       → most recent notes for a challenge
    deleteEntry(id)                 → DELETE
    countStreak(dates, today) [static, pure] → streak algorithm (testable)

  STREAK ALGORITHM:
    Queries distinct successful days (last 100), walks backwards from today.
    If today is missed, yesterday still counts (streak is "pending").
    If both today and yesterday are missed, streak is broken.
    Uses string-based date comparison to avoid DST edge cases.

SETTINGS (SharedPreferences only):

  SettingsRepository (lib/data/settings_repository.dart)
  Pattern: Singleton, direct SharedPreferences calls

  Stored keys:
    settings_dark_mode              bool?
    settings_language               String?
    notifications_enabled           bool (default: false)
    sound_effects_enabled           bool (default: true)
    notification{1,2,3}Enabled      bool
    notification{1,2,3}TimeHour     int
    notification{1,2,3}TimeMinute   int
    onboarding_complete             bool
    comfort_zone_level              int (default: 1)
    last_opened_date                String (ISO date)
    last_celebrated_streak          int (default: 0)

  Also used by Kotlin BootReceiver directly (no bridge needed).

─── 3.6 COMFORT ZONE LEVEL (CZL) SYSTEM ────────────────────────────────────────

File: lib/logic/comfort_zone_logic.dart

Five levels, each with a name and description:
  1 — Warming Up        "Micro-interactions — low stakes, high growth"
  2 — Breaking the Ice  "Brief exchanges with real humans"
  3 — Holding the Floor "Sustained conversations and presence"
  4 — Taking Risks      "Vulnerability, compliments, assertiveness"
  5 — The Bold Zone     "High-stakes social challenges"

Level assignment (assignLevel):
  Sorts entire catalog by XP, finds this challenge's percentile:
    0–20%  → level 1
    20–40% → level 2
    40–60% → level 3
    60–80% → level 4
    80%+   → level 5

  This is deterministic and catalog-relative — adding new challenges can
  shift all level assignments.

Level unlocking (recordSuccessAndCheckLevelUp):
  Only completions of challenges AT or ABOVE the user's current level count.
  After completionsToUnlock (= 3) such completions at current level → level up.
  Completion counts are persisted per level in SharedPreferences:
    key: 'czl_completions_' + level number

filterByCzl(catalog, currentLevel):
  Returns only challenges assigned level ≤ currentLevel. This is what
  czlFilteredChallengesProvider applies before other filters.


─── 3.7 DAILY MISSIONS SYSTEM ──────────────────────────────────────────────────

File: lib/logic/daily_missions_logic.dart

Replaces the old single-daily-challenge with a three-tier Mission Board.

Three tiers per day:
  Comfort — from the bottom third of the catalog by XP (non-flirt preferred)
  Growth  — from the middle third
  Bold    — from the top third (falls back to top 5 overall if too small)

Selection algorithm (DailyMissionsLogic.getTodayMissions):
  1. Load full catalog for the current language.
  2. Filter out flirt challenges (preferred pool).
  3. Sort by XP, split into thirds.
  4. If stored date ≠ today OR any stored ID is null → re-roll all three.
  5. Randomly pick one challenge per tier, persist IDs + date.
  6. Return List<DailyMission> with completed flags from SharedPreferences.

markCompleted(tier) → sets the tier's done key to true.

Persistence keys (SharedPreferences):
  daily_missions_date, daily_missions_{comfort|growth|bold}_id,
  daily_missions_{comfort|growth|bold}_done

XP BONUS: ChallengeDoneScreen adds a 10% bonus (rounded) to earned XP when
isDailyMission = true and the challenge was not aborted.

─── 3.9 ACTIVE CHALLENGE SCREEN ────────────────────────────────────────────────

File: lib/routes/active_challenge_screen.dart  (499 lines)

ConsumerStatefulWidget with TickerProviderStateMixin + WidgetsBindingObserver.

State:
  mainTimer         int    seconds remaining (decremented by wall-clock diff)
  abortLockTimer    int    15 → 0 countdown before abort button appears
  _startTime        DateTime  absolute start time
  _endTime          DateTime  _startTime + challenge.time seconds
  _progressController  AnimationController  drives continuous SyntraXpBar fill
  _fadeController   AnimationController  fade-in on entry

Two Future.doWhile() loops drive the timers (no periodic Timer):
  mainTicker:     checks wall-clock diff every second, syncs mainTimer
  abortLockTicker: decrements abortLockTimer every second until 0

Background handling (WidgetsBindingObserver):
  On paused: schedules a "time's up" notification at _endTime via
             NotificationManager.sendNotification(scheduledTime: _endTime)
  On resumed: re-syncs mainTimer from wall-clock, cancels scheduled notification
              if time hasn't expired yet, re-syncs _progressController.

10-second warning: VibrationService.timerWarning() fires at mainTimer == 10.
Timer up: VibrationService.timerEnd() + immediate local notification.

rewardFactor:
  1.0  — timer expired naturally (full XP)
  0.8  — user tapped Done before timer expired
  -0.5 — user tapped Abort (records 'tried', earns 0 XP)

_finishChallenge(rewardFactor):
  Uses Navigator.of(context).push<double>(MaterialPageRoute → ChallengeDoneScreen).
  On ChallengeDoneScreen returning a result, cancels any pending notification,
  calls widget.onDone?(result), then popUntil(isFirst).

PopScope(canPop: false) prevents back-button navigation during a live challenge.

UI sub-widgets (file-private):
  _TimerBar       Container with countdown text + SyntraXpBar
  _HelpButton     OutlinedButton → opens NotSureWhatToSayDialog
  _AbortButton    TextButton in error color, slide-in when lock expires


─── 3.10 CHALLENGE DONE SCREEN ─────────────────────────────────────────────────

File: lib/routes/challenge_done_screen.dart  (537 lines)

ConsumerStatefulWidget. Receives: Challenge, rewardFactor, durationSeconds?,
onDone? callback, isDailyMission flag.

Computed state:
  _isAborted   → rewardFactor < 0
  _earnedXp    → isAborted ? 0 : (challenge.xp * rewardFactor).round()
  _bonusXp     → isDailyMission && !isAborted ? (_earnedXp * 0.1).round() : 0
  _totalXp     → _earnedXp + _bonusXp
  _status      → isAborted ? 'tried' : 'success'

UI on success:
  - Trophy icon in primaryContainer circle
  - "Congratulations" headline
  - Coach message in italic quote box (deterministic per challenge ID using hash)
  - XP chip with TweenAnimationBuilder (counts up 0 → _totalXp in 900ms)
  - SyntraXpBar animates rewardFactor over 2300ms
  - Daily bonus badge (scale-in animation) if _bonusXp > 0
  - _SurveyWidget (mood emoji scale + perception emoji scale + notes text field)

UI on abort:
  - Meditation icon in surfaceContainerHighest circle
  - "Too bad" headline
  - failureCopy body text
  - "+0 Aura Points" chip

_onBackToHome:
  1. Auto-submits survey if not already submitted
  2. Writes logbook entry (LogbookRepository.addEntry with feeling, perception, notes)
  3. If success: calls comfortZoneLevelProvider.notifier.recordSuccessAndCheckLevelUp

─── 3.16 NOTIFICATION SYSTEM ────────────────────────────────────────────────────

Two classes manage notifications. They overlap and have some redundancy.

─ SyntraNotificationService (lib/services/syntra_notification_service.dart) ─────
~850 lines. The primary service initialized at startup.

Responsibilities:
  - Flutter plugin initialization (Android + iOS DarwinInitializationSettings)
  - MethodChannel setup for native Android bridge
  - Permission requests (Android: POST_NOTIFICATIONS + SCHEDULE_EXACT_ALARM;
    iOS: UNUserNotificationCenter via IOSFlutterLocalNotificationsPlugin)
  - scheduleExactNotification(): tries native Android first, falls back to
    flutter_local_notifications zonedSchedule()
  - batchScheduleNotifications(): native batch call on Android, individual
    fallback otherwise
  - cancelNotification(id), cancelAllNotifications()
  - getScheduledNotifications(): reads from SharedPreferences JSON store
  - rescheduleAllNotifications(): re-schedules from stored JSON list (used
    by boot handler via handleBootCompleted callback)
  - showNotificationNow(): immediate notification (debugging)
  - setNativeNotificationsEnabled(bool): syncs to native layer

Notification metadata is mirrored in SharedPreferences under key
'syntra_scheduled_notifications' as a JSON array. This allows the service
to reschedule from Dart without a separate database.

Notification channels:
  syntra_reminders   Daily motivation reminders
  syntra_challenges  Challenge timer "time's up"
  syntra_system      System messages

─ NotificationManager (lib/logic/notification_manager.dart) ─────────────────────
~640 lines. Higher-level scheduling logic that wraps SyntraNotificationService.

Responsibilities:
  - scheduleDailyReminders(): reads all enabled slots from SharedPreferences,
    calculates next 7 occurrences of each enabled time slot, batch-schedules
    via SyntraNotificationService.
  - cancelAllNotifications(): triple-cancels (flutter plugin + service + native
    MethodChannel directly — defensive coding)
  - sendNotification(channelId, title, body, scheduledTime): used by
    ActiveChallengeScreen for the "time's up" background notification
  - sendImmediateNotification(): wrapper for when timer expires in foreground
  - cancelNotification(id): cancels a specific scheduled notification
  - initialize(): local plugin init (separate from SyntraNotificationService init)

─ Android Native Layer ──────────────────────────────────────────────────────────

SyntraNotificationManager.kt:
  Uses AlarmManager.setExactAndAllowWhileIdle() for exact timing even in Doze.
  Creates three notification channels on app install.
  scheduleExactAlarm(id, title, body, triggerTime, channelId)
  batchScheduleNotifications(...)
  cancelNotification(id), cancelAllNotifications()
  showNotificationNow(...)

SyntraNotificationReceiver.kt (BroadcastReceiver):
  Triggered by AlarmManager. Calls NotificationManager.notify() to display.

SyntraBootReceiver.kt (BroadcastReceiver):
  Listens for: ACTION_BOOT_COMPLETED, LOCKED_BOOT_COMPLETED, QUICKBOOT_POWERON,
               PACKAGE_REPLACED, TIMEZONE_CHANGED, TIME_SET
  On any trigger: reads SharedPreferences for notification schedules,
  reschedules all via SyntraNotificationManager.
  This runs without a Dart runtime — pure Kotlin/Android.

Android permissions required:
  POST_NOTIFICATIONS (Android 13+)
  SCHEDULE_EXACT_ALARM (Android 12+)
  Battery optimization exemption (requested in-app)

SECTION 5 — CURRENT PROBLEMS & REMAINING GAPS
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

These are real issues visible in the current code.

────────────────────────────────────────────────────────────────────────────────
PROBLEM 1: LOGBOOK SCHEMA IS MISSING MIGRATIONS FOR feeling/perception COLUMNS
────────────────────────────────────────────────────────────────────────────────

LogbookRepository opens the database at version 2 with one migration:
  v1 → v2: ALTER TABLE logbook ADD COLUMN duration_seconds INTEGER

But the logbook table also stores feeling and perception columns.
These were added by altering the initial schema in the CREATE TABLE statement
but there is NO migration that adds them for existing users upgrading from v1.
Any user who had the app before these columns were added will get
"table logbook has no column named feeling" errors on addEntry().

Fix: increment to version 3 and add two ALTER TABLE migrations for feeling and
perception in the onUpgrade handler.

────────────────────────────────────────────────────────────────────────────────
PROBLEM 2: challenge_id TYPE MISMATCH BETWEEN DB AND DART
────────────────────────────────────────────────────────────────────────────────

Challenge.id is a String in Dart ("90", "91"...).
The logbook table's challenge_id column is INTEGER in SQLite.
When addEntry() is called, challenge.id (a String) is passed directly and
SQLite coerces it to integer — this works if the string is numeric.
But completedChallengeIds() does `r['challenge_id'].toString()` as a workaround.

If a challenge ever has a non-numeric ID (e.g. "custom_1"), this will break
silently or produce wrong IDs. The DB column should be TEXT, or the Dart model
should use int IDs consistently.

────────────────────────────────────────────────────────────────────────────────
PROBLEM 3: LARGE MONOLITHIC SCREEN FILES
────────────────────────────────────────────────────────────────────────────────

  challenges_screen.dart     965 lines
  onboarding_screen.dart     864 lines
  challenge_done_screen.dart 537 lines
  statistics_screen.dart     659 lines
  settings_screen.dart       518 lines

Each is a single file with many private widget classes defined at the bottom.
This works but makes navigation (finding a specific widget), code reviews, and
testing difficult. The pattern should be: each meaningful sub-widget in its
own file under a screens/<feature>/widgets/ subdirectory.

────────────────────────────────────────────────────────────────────────────────
PROBLEM 4: MIXED NAVIGATION — Navigator.push INSIDE GoRouter SCREENS
────────────────────────────────────────────────────────────────────────────────

ActiveChallengeScreen uses Navigator.of(context).push<double>(MaterialPageRoute)
to reach ChallengeDoneScreen. This is not part of GoRouter. Consequence:
  - ChallengeDoneScreen is not accessible via /challenge_done deep link from
    this path.
  - Back button behavior is not managed by GoRouter.
  - StreakCelebrationScreen is also pushed via Navigator.push from
    ChallengeDoneScreen and HomeBar.

These should all use GoRouter.push() with extra data. The return value
pattern (push returning a result) is supported via GoRouter.push<T>().

────────────────────────────────────────────────────────────────────────────────
PROBLEM 5: routerNotifier IS A GLOBAL LATE VARIABLE
────────────────────────────────────────────────────────────────────────────────

router_notifier.dart declares:
  late final RouterNotifier routerNotifier;

This is a module-level global variable, not a Riverpod provider. It's accessed
from router.dart's GoRouter configuration (appRouter, also a global). This is
a known limitation of go_router + Riverpod — the router cannot be a provider
because GoRouter itself needs to be a const-ish global. However, it means
RouterNotifier is not overridable in tests.

────────────────────────────────────────────────────────────────────────────────
PROBLEM 6: CZL LEVEL ASSIGNMENT IS CATALOG-RELATIVE
────────────────────────────────────────────────────────────────────────────────

ComfortZoneLogic.assignLevel() sorts the entire catalog by XP and assigns
levels by percentile. This means:
  - Adding or removing challenges can change the level of ALL existing challenges.
  - A user's stored completion count (czl_completions_N) may now reference
    challenges that moved to a different level.
  - There is no stable level mapping for a challenge.

A fixed level field per challenge (in challenges.json) would be more stable
and predictable.

────────────────────────────────────────────────────────────────────────────────
PROBLEM 7: NOTIFICATION ARCHITECTURE IS OVER-ENGINEERED AND REDUNDANT
────────────────────────────────────────────────────────────────────────────────

There are now TWO notification manager classes doing overlapping things:
  - SyntraNotificationService (~850 lines)
  - NotificationManager (~640 lines)

NotificationManager.cancelAllNotifications() calls:
  1. _notificationsPlugin.cancelAll() (Flutter plugin)
  2. SyntraNotificationService.instance.cancelAllNotifications() (which itself
     calls MethodChannel + flutter plugin)
  3. MethodChannel('syntra_notifications').invokeMethod('cancelAllNotifications')
     AGAIN directly
  4. Clears SharedPreferences key

This is triple-cancelling with duplicate code paths. The two classes should
be merged or one should clearly own the responsibility.

────────────────────────────────────────────────────────────────────────────────
PROBLEM 8: priming_screen.dart AND mindset_screen.dart ARE NOT ROUTED
────────────────────────────────────────────────────────────────────────────────

lib/routes/priming_screen.dart (243 lines) and mindset_screen.dart (287 lines)
exist and contain full UI implementations but are NOT registered in GoRouter
and not navigated to from anywhere visible in the code. They are either:
  - Work in progress (intended for future navigation)
  - Dead code from an abandoned feature branch

They should be either wired up with routes or deleted.

────────────────────────────────────────────────────────────────────────────────
PROBLEM 9: Challenge MODEL HAS MUTABLE FIELDS
────────────────────────────────────────────────────────────────────────────────

All fields in Challenge are declared with `var` (mutable):
  String id;
  String title;
  ...

These should be `final`. Challenge instances are read-only once loaded from
JSON — nothing modifies them after construction. Immutability makes bugs
less likely and enables const constructors.

────────────────────────────────────────────────────────────────────────────────
PROBLEM 10: FutureProvider CALLS SharedPreferences.getInstance() ON EVERY READ
────────────────────────────────────────────────────────────────────────────────

ChallengeFiltersNotifier and other Notifiers call
SharedPreferences.getInstance() on every write (setTypeFilter, setFlirtFilter,
etc.). While SharedPreferences caches the instance internally, the correct
pattern is to obtain the SharedPreferences instance once in a provider
(sharedPreferencesProvider) and inject it, making the code testable and
avoiding the implicit singleton.

SECTION 7 — iOS NOTIFICATION STATUS (UPDATED)
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

The iOS notification gap identified in the previous analysis has been PARTIALLY
fixed:

FIXED:
  SyntraNotificationService.initialize() now includes DarwinInitializationSettings
  with all request permissions set to false (deferred — correct pattern).
  Permission is requested later via IOSFlutterLocalNotificationsPlugin.requestPermissions().
  _scheduleWithFallback() includes DarwinNotificationDetails in NotificationDetails.

STILL PRESENT:
  1. The MethodChannel branch in scheduleExactNotification() is guarded by
     Platform.isAndroid. On iOS, it falls through to _scheduleWithFallback()
     which uses flutter_local_notifications.zonedSchedule(). This is correct.
     BUT: AndroidNotificationDetails is still included in the fallback path.
     On iOS, only DarwinNotificationDetails is needed — including Android details
     is harmless but clutters the code.

  2. The native scheduling layer (SyntraNotificationManager.kt, BootReceiver.kt)
     does not exist on iOS. iOS relies on UNUserNotificationCenter via the
     Flutter plugin. This is the correct approach for iOS — the key constraint
     is that iOS limits apps to 64 scheduled local notifications at once
     (UNUserNotificationCenter). The current 7-days-in-advance × 3-slots = 21
     notifications is within this limit.

  3. Boot recovery does not exist on iOS and cannot (iOS doesn't allow
     BOOT_COMPLETED equivalent). This means if the user's scheduled notifications
     expire (after 7 days without opening the app), they won't be rescheduled
     until the app is opened. This is a known iOS limitation; document it.

STATUS: iOS notifications should work functionally for most users. The main
remaining risk is the 7-day expiry with no reschedule on iOS if the app is
not opened.
