SECTION 1 — WHAT THE APP IS
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Syntra is an offline-first Flutter app for building social confidence through
deliberate social challenges. Users are presented with real-world social tasks
(e.g. "start a conversation with a stranger", "give someone a compliment"),
accept them with a countdown timer, and log whether they succeeded or not.
"Aura Points" (XP) is awarded on success, weekly streaks are tracked, and every
attempt is stored in a logbook.

The app is structured around a progression system: a ten-level Comfort Zone
Level (CZL) which gates which challenges are visible, unlocking harder content
as the user completes enough challenges at their current level. The threshold
per level grows (3 → 5 → 8 → 12 → 16 → 20 → 25 → 30 → 35 completions) so
early progress is fast and later mastery requires genuine sustained effort.

Each day a Mission Board offers three tailored challenges (Comfort / Growth /
Bold tier), with a 10% Aura bonus for completing daily missions. The app
reminds users via local notifications and celebrates streaks with an animated
screen.

The prediction-reality gap system — the most psychologically differentiated
feature — is now fully shipped: users rate pre-challenge anxiety (1–5) on the
Priming Screen; the data is stored in logbook.pre_anxiety; PredictionGapCard
surfaces the gap per-challenge and overall on the statistics screen.

There is no backend, no account system, and no cloud sync. All data lives on
the device.

SECTION 3 — EVERY SYSTEM IN DETAIL
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

─── 3.1 APP STARTUP ────────────────────────────────────────────────────────────

main() runs these steps synchronously before runApp():

  1. WidgetsFlutterBinding.ensureInitialized()
  2. tz.initializeTimeZones() — timezone data for notification scheduling
  3. SharedPreferences.getInstance() — loaded once; instance passed both to
     SettingsRepository.configure() and to the ProviderScope override.
     This guarantees both Riverpod and non-Riverpod code (NotificationManager)
     share the exact same SharedPreferences instance.
  4. SettingsRepository.configure(prefs) — makes SettingsRepository.instance
     available to non-Riverpod callers (e.g. NotificationManager) without
     requiring a BuildContext or Ref.
  5. _migrateSettingsJson() — one-time migration: reads legacy settings.json
     from documents dir, writes values to SharedPreferences, deletes the file.
     Best-effort (errors ignored).
  6. SettingsRepository.instance.loadOnboardingComplete() — read before router
     init so the router can set initialLocation correctly.
  7. routerNotifier = RouterNotifier(onboardingDone) — ChangeNotifier for GoRouter.
  8. SoundService.init() — audioplayers initialization (must happen before
     first playback call in the UI).
  9. SyntraNotificationService.instance.initialize() — Flutter plugin init.
  10. runApp(ProviderScope(overrides: [sharedPreferencesProvider.overrideWithValue(prefs)],
             child: SyntraApp()))

IMPORTANT CHANGE FROM PREVIOUS VERSION:
  _copyDatabaseIfNeeded() is REMOVED. There is no longer an asset copy step.
  The logbook.db is created fresh on first launch by sqflite's onCreate callback
  with schema version 1. The old challenge_database.db asset no longer exists.
  The logbook table is created from scratch; challenge catalog comes from JSON.

SyntraApp (ConsumerWidget):
  - Watches themeModeProvider → ThemeMode (light/dark/system)
  - Watches localeProvider → Locale (en/de)
  - Renders MaterialApp.router with AppTheme.light(), AppTheme.dark(),
    appRouter (GoRouter), S.delegate for localization.
  - builder: wraps child in MediaQuery with textScaler.clamp(min: 1.0, max: 1.3)
    so large system font-size settings do not break layouts while still allowing
    mild scaling. This is a defensive accessibility measure.


─── 3.2 NAVIGATION ─────────────────────────────────────────────────────────────

Router: go_router (GoRouter) with a ChangeNotifier-based refresh.

ROUTE GUARD (router.dart):
  GoRouter.redirect checks routerNotifier.onboardingComplete:
    - Not done + not on /onboarding → redirect to /onboarding
    - Done + on /onboarding → redirect to /
    - Otherwise → null (no redirect)

NAMED ROUTES (AppRoutes abstract class):
  /                    → HomeBar (bottom-nav shell)
  /onboarding          → OnboardingScreen
  /priming             → PrimingScreen (extra: _PrimingArgs)
  /active_challenge    → ActiveChallengeScreen (extra: _ActiveChallengeArgs)
  /challenge_done      → ChallengeDoneScreen (extra: _ChallengeDoneArgs)
  /logbook             → LogbookPage
  /about               → AboutNotePage
  /streak_celebration  → StreakCelebrationScreen (extra: _StreakCelebrationArgs)
  /level_up            → LevelUpScreen (extra: _LevelUpArgs)
  /badge_unlocked      → BadgeUnlockedScreen (extra: _BadgeUnlockedArgs)
  /badges              → AllBadgesPage  [NEW]

  NOTE: /level_up and /badge_unlocked were previously reached via Navigator.push;
  they are now proper GoRouter routes. LogbookDetailPage still uses
  LogbookDetailPage.show() (a static method wrapping showModalBottomSheet or
  Navigator.push) — it passes entry data as a plain Map<String,dynamic> with
  title String.

EXTENSION HELPERS (AppNavigation on BuildContext):
  context.pushPriming(challenge, {isDailyMission})       → push priming
  context.goPriming(challenge, {isDailyMission})         → go('/') then push priming
  context.pushActiveChallenge(challenge, {isDailyMission, overrideTime})
  context.goActiveChallenge(challenge, {isDailyMission, overrideTime})
  context.pushChallengeDone(challenge, rewardFactor, {durationSeconds, isDailyMission})
  context.goLogbook()
  context.goLogbookDetail(entry, title)
  context.goAbout()
  context.goStreakCelebration(streak, isMilestone)
  context.goLevelUp(newLevel)            [NEW]
  context.goBadgeUnlocked(badge)         [NEW]
  context.goAllBadges()                  [NEW]

  goPriming() is a "try again" helper: calls go('/') to clear the stack, then
  immediately pushes priming — both state changes are batched into a single
  rebuild to avoid visible flash.

  _ActiveChallengeArgs now carries an optional overrideTime: int? field, which
  allows the timer to be overridden for testing or special flows.

BOTTOM NAVIGATION (HomeBar):
  Uses a PageView + NavigationBar. Tabs:
    0 — ChallengesScreen    (explore icon)
    1 — DailyChallengeScreen (calendar icon)
    2 — ProfileScreen        (bar_chart icon)
    3 — SettingsScreen       (settings icon)

  PageView is swipeable (BouncingScrollPhysics).
  Programmatic tab switches use homeTabIndexProvider (StateProvider<int>).
  HomeBar listens to homeTabIndexProvider and calls animateToPage().

  SCROLL-TO-TOP BEHAVIOR:
  Re-tapping the already-active tab fires the corresponding scroll-to-top
  provider (challengesScrollToTopProvider, dailyScrollToTopProvider,
  profileScrollToTopProvider, settingsScrollToTopProvider). Each screen
  listens via ref.listen and animates its ScrollController to offset 0.
  Guard: tap only fires scroll if !_isAnimating (prevents re-entrant trigger).

REMAINING INCONSISTENCY:
  ActiveChallengeScreen navigates to ChallengeDoneScreen via GoRouter.push<double>
  (via context.pushChallengeDone). The return value (rewardFactor double) flows
  back when the user pops ChallengeDoneScreen. This is now consistently a GoRouter
  push, not a Navigator push — the previous mixed-navigation concern is resolved.

─── 3.4 CHALLENGE DATA LAYER ───────────────────────────────────────────────────

CATALOG (read-only, JSON):

  ChallengeRepository (lib/data/challenge_repository.dart)
  Pattern: Singleton, in-memory cache per language

  loadChallenges(languageCode) → Future<List<Challenge>>:
  1. Returns cached list if language matches.
  2. Loads assets/data/challenges.json (id, xp, timer, type, flirt, level, env).
  3. Loads assets/data/translations/{languageCode}.json (title, description, hints).
  4. Falls back to 'en' translations if a key is missing.
  5. Builds List<Challenge> and stores in _cache.

  invalidate() clears the cache (e.g., on language switch).

LOGBOOK (read/write, SQLite):

  LogbookRepository (lib/data/logbook_repository.dart)
  Pattern: Singleton, lazy database open

  Database: logbook.db (path via getDatabasesPath())
  Schema version: 1
  Created fresh on first install. No asset copy. No migration path from old
  versions. (If upgrading from a build that had the asset copy, the old DB
  persists; schema v1 is forward-compatible as the column was always named
  'aura' in the current DDL.)

  logbook table (current schema):
    id               INTEGER PK AUTOINCREMENT
    challenge_id     TEXT     (sequential string ID, e.g. "42")
    status           TEXT     'success' | 'tried'
    aura             INTEGER  Aura (XP) awarded (was 'earned' in older builds)
    timestamp        DATETIME ISO8601 string
    notes            TEXT     nullable
    feeling          INTEGER  nullable, 0–4 emoji scale (4 = very satisfied/calm)
    perception       INTEGER  nullable, 0–4 emoji scale
    duration_seconds INTEGER  nullable
    pre_anxiety      INTEGER  nullable, 1–5 scale (5 = very nervous)

  COLUMN RENAME NOTE: The column was 'earned' in older builds. It is now 'aura'
  in the CREATE TABLE DDL. Any DB created by a prior build has 'earned'; the
  repository now reads/writes 'aura'. This is a silent schema discrepancy on
  upgrade paths that do not wipe data. A v1→v2 migration renaming the column
  is the correct fix (Problem 1 below).

  Indexes (created in onCreate):
    idx_logbook_status_challenge ON logbook(status, challenge_id)
    idx_logbook_timestamp        ON logbook(timestamp)
    idx_logbook_challenge        ON logbook(challenge_id)

  Key methods:
    addEntry(...)                        → INSERT
    filteredEntries({limit, offset,      → paginated SELECT with optional
      status, challengeIds})               status + ID filter
    allEntries({limit, offset})          → paginated SELECT DESC
    entryById(id)                        → SELECT by PK
    overviewStats()                      → aggregate: totalAura, todayAura,
                                           completedAllTime, completedToday,
                                           weekStreak, pendingWeekStreak,
                                           minutesBrave
    weeklyAuraByWeek({weeks=52})         → Map<isoWeekKey, aura>
    currentWeekAura()                    → int Aura earned this Mon–Sun week
    weeklyAura({days=7})                 → List<int> Aura per day (oldest→newest)
    weeklyChallengeCounts({days=7})      → List<List<int>> [successes, tried] per day
    activityHeatmap({weeks=12})          → Map<dateStr, count>
    completedChallengeIds()             → Set<String> all success challenge_ids
    latestCompletionDates()             → Map<String, DateTime> newest per challenge
    lastNotesForChallenge(id)           → most recent notes + timestamp
    entriesForChallenge(id, {limit=100}) → all entries for one challenge (for gap)
    allEntriesForGap()                   → SELECT pre_anxiety, feeling WHERE both NOT NULL
    deleteEntry(id)                      → DELETE; clears frozen weeks if table empty
    challengesCompletedThisWeek()       → int (for weekly goal progress)
    moodHistoryForChallenge(id)         → List<int> feeling scores
    averageMoodPerDay({days=14})        → last 20 individual entries (not averaged by day)
    countStreak(dates, today) [static]  → legacy daily streak (test suite compat)
    clearAllEntries()                   → DELETE all rows (used by fake_data_seeder)

  WEEKLY STREAK ALGORITHM (lib/logic/weekly_streak_logic.dart):
    Pure, side-effect-free. Uses ISO 8601 week numbering (Mon-aligned).
    kWeeklyXpThreshold = 300 Aura — minimum weekly Aura for a streak week.
    startOfIsoWeek(date) → DateTime (Monday of the week containing date)
    isoYearWeek(date) → String (e.g. "2026-W18")
    countStreak(): walks back from current week, counts consecutive qualifying
      weeks. The current in-progress week counts immediately once it hits 300.
    countPendingStreak(): starts from last week — shows streak-in-grey when
      the current week hasn't activated yet.
    countStreakAutoFreeze(): auto-applies available streak freeze charges to
      consecutive missed past weeks.

SETTINGS (SharedPreferences only):

  SettingsRepository (lib/data/settings_repository.dart)
  Pattern: Singleton via configure(), injected into Riverpod via override.

  KEY CHANGE: Theme is now stored as a string ("light"/"dark"/"system") under
  _keyThemeMode = 'settings_theme_mode', not as a bool. loadThemeMode() migrates
  from the legacy _keyDarkMode bool key on first call after upgrade. The legacy
  key is kept for backward compat (saveDarkMode still writes it, but no new code

─── 3.19 PREDICTION-REALITY GAP SYSTEM ──────────────────────────────────────────

[NEW SYSTEM — fully shipped since 2026-04-25 version]

Files:
  lib/logic/prediction_gap_logic.dart
  lib/providers/prediction_gap_providers.dart
  lib/widgets/prediction_gap_card.dart
  lib/routes/statistics/overall_prediction_card.dart

DATA MODEL:
  pre_anxiety is stored in logbook.pre_anxiety on a 1–5 scale where 5 = very nervous.
  feeling is stored in logbook.feeling on a 0–4 scale where 4 = very satisfied/calm.

  To compare both on the same scale, feeling is converted:
    actualAnxiety = 5 − feeling.clamp(0, 4)  → result is 1–5, high = nervous

  gap = preAnxiety.clamp(1,5) − actualAnxiety
    Positive gap: user felt calmer than expected (confidence builder)
    Negative gap: user felt more nervous than expected (reality check)

TONE CATEGORIES (PredictionGapTone enum):
  veryCalm   — averageGap > 1.5   ("Much calmer than expected")
  calm       — averageGap > 0.5   ("Calmer than expected")
  accurate   — |averageGap| < 0.5 ("Accurately predicted")
  nervous    — averageGap ≤ −0.5  ("More nervous than expected")
  tough      — averageGap < −1.5  ("Much tougher than expected")

ChallengeGapInsight fields:
  attempts          — number of valid entries (both pre_anxiety and feeling non-null)
  averageGap        — mean gap across all valid entries
  calmThanPredicted — count of entries where gap > 0

PredictionGapLogic.compute(entries):
  Returns null if fewer than minAttempts (3) valid entries.
  "Valid" means both pre_anxiety and feeling are non-null integers.

PredictionGapCard widget:
  Uses DetailCard (icon: Icons.psychology_rounded) as its container.
  Renders: tone message text, three _StatBlock cells (attempts, avg gap, calmer count).
  formatGap: positive values prefixed with "+".

OverallPredictionCard:
  Thin ConsumerWidget wrapping overallPredictionGapProvider.
  Renders nothing (SizedBox.shrink) while loading, on error, or if null.
  Placed in ProfileScreen below AverageMoodCard.

Per-challenge gap: predictionGapProvider.family(challengeId) renders a
PredictionGapCard in ChallengeDetailScreen when ≥3 entries exist.

─── 3.23 GAMIFICATION LOOP ─────────────────────────────────────────────────────

Full user loop:

  1. Onboarding → set CZL → unlock initial challenge pool (levels ≤ chosen)
  2. Open app → see challenges filtered by CZL (1–10) + applied filters
  3. Accept a challenge (or start a daily mission)
  4. Priming screen → pre-challenge anxiety rating (1–5) → motivational framing
  5. Timer runs → go do it in the real world
  6. Return → mark result → complete survey (mood, perception, notes)
  7. Aura awarded → logged with pre_anxiety → weekly Aura accumulates
  8. Weekly Aura ≥ 300 → current week "active" → weekly streak active
  9. Streak freezes auto-apply to missed past weeks (if freezes available)
  10. CZL completions++ → at threshold → level-up screen → new challenges unlocked
  11. New badge earned → badge_unlocked_screen celebration (once per badge)
  12. Stats/Profile: Aura charts, gap insight, badges, weekly goal
  13. Notifications remind user each day via configurable time slots

Sound effects (SoundService):
  playClick() — nav bar taps
  playDing() — challenge start
  playSuccess() — challenge success
  playError() — challenge abort/failure
  SoundService.init() is called at app startup.

Haptic feedback:
  HapticFeedback.selectionClick() on nav bar press
  VibrationService.start()        — challenge timer starts
  VibrationService.timerWarning() — 10 seconds remaining
  VibrationService.timerEnd()     — timer hits zero
  VibrationService.success()      — successful completion
  VibrationService.milestone()    — streak milestone

────────────────────────────────────────────────────────────────────────────────
Q10: czlCompletionsProvider CALLS getCompletionsAtCurrentLevel() VIA .notifier
────────────────────────────────────────────────────────────────────────────────
lib/providers/statistics_providers.dart:
  czlCompletionsProvider = Provider<int>((ref) {
    ref.watch(comfortZoneLevelProvider);
    ref.watch(statisticsRefreshProvider);
    return ref.read(comfortZoneLevelProvider.notifier).getCompletionsAtCurrentLevel();
  });

ref.read() inside a Provider is a code smell — it creates a non-reactive read
in what appears to be a reactive provider. If the notifier's internal state
changes without triggering comfortZoneLevelProvider's own change notification,
czlCompletionsProvider will not update. This is low-risk because SharedPreferences
reads are synchronous and the watch on comfortZoneLevelProvider covers the common
path, but it should be made explicit.

SECTION 10 — PSYCHOLOGICAL DESIGN ANALYSIS
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

────────────────────────────────────────────────────────────────────────────────
10.1 WHAT THE APP GETS RIGHT
────────────────────────────────────────────────────────────────────────────────

GRADUATED EXPOSURE (STRONG — now stronger with 10 levels)
The CZL system is a direct implementation of clinical exposure therapy.
Ten levels from Level 1 ("internal discomfort only, no words required") to
Level 10 ("just outside what feels acceptable — you feel the weight, you go anyway")
form an extraordinarily precise SUDS (Subjective Units of Distress) hierarchy.
The new level descriptions are psychologically sophisticated — they identify
exactly which component of the social interaction creates the anxiety (the opener,
staying present, revealing something personal, the visibility of the approach, the
sustained audience). This mirrors systematic desensitization more faithfully than
any comparable consumer app.

PREDICTION-REALITY GAP (NOW IMPLEMENTED — strongest evidence-based feature)
This is the most clinically validated mechanism for reducing social anxiety.
Research consistently shows that anxious people catastrophically over-predict
aversive outcomes. Showing the gap between expectation and reality — repeatedly,
across challenges — is what creates lasting belief change, not just behavioral change.
The full pipeline is now in place:
  - Pre-challenge anxiety rating (1–5) captured on PrimingScreen
  - Post-challenge feeling (0–4) captured on ChallengeDoneScreen survey
  - Gap computation in PredictionGapLogic with tone categorization
  - Per-challenge and aggregate display via PredictionGapCard

The one remaining gap (TODO H, S7): showing the per-session comparison immediately
on the ChallengeDoneScreen ("You expected 4/5 — you felt 2/5") would be the most
powerful reinforcement moment. Currently the gap is only visible on the detail
screen (historical view). The immediate comparison is what triggers the "oh, I was
wrong about this" insight that drives habit change.

BEHAVIORAL COMMITMENT (STRONG)
The 15-second abort lock (_kAbortLockSeconds = 15) is a well-designed
implementation of commitment theory. Brief tolerance of discomfort, not avoidance,
is what produces habituation. The lock is the right call.

PRIMING / IMPLEMENTATION INTENTIONS (GOOD)
PrimingScreen gives contextual framing before the timer starts. Adding the anxiety
rating before the challenge (implementation intention with an emotional baseline)
is now the key data capture point for the gap system.

IMMEDIATE REINFORCEMENT LOOP (STRONG)
Challenge → timer → done → Aura count-up → coach message → survey.
The full loop is tight and well-timed.

WEEKLY STREAK DESIGN (STRONG)
kWeeklyXpThreshold = 300, Mon–Sun, freeze mechanic. The design is sound:
achievable in a realistic week, resilient to disruption, motivationally urgent.

────────────────────────────────────────────────────────────────────────────────
10.2 WHAT IS MISSING OR STILL WEAK
────────────────────────────────────────────────────────────────────────────────

PREDICTION GAP NOT SHOWN AT THE RIGHT MOMENT
The gap insight is now displayed historically (detail screen, stats screen).
But the highest-impact moment is the milliseconds right after completing a
challenge — when the emotional memory is freshest and the cognitive dissonance
("I thought this would be terrible, it was fine") is most salient. The done
screen should show: "You expected [pre_anxiety icon], you felt [feeling icon]."
Even without aggregation. Even on the first attempt.

NO INSIGHT LAYER ON THE LOGBOOK
Rich data exists but is only displayed chronologically. Missing derived insights:
  - "85% solo success vs. 40% group success"
  - "Average mood after challenges: 3.8/5"
  - "You haven't tried a Bold challenge in 2 weeks"

ABORT IS STILL FRAMED AS FAILURE
Even an aborted challenge involved showing up and starting. The app should
celebrate attempts more explicitly. Consider renaming "Tried" to "Attempted"
and framing: "Partial exposure still reduces anxiety — you did the hardest part."

SOCIAL PROOF IS FAKE AND INERT
"X others have done this challenge" (800–4499 hash) is not doing psychological
work and is technically misleading. Real anonymized notes require backend (TODO K).

COACH MESSAGES ARE NOT CONTEXTUAL
7 generic messages, deterministic by challenge ID. After a flirt challenge the
message should differ from a group challenge. Pool by type and draw from the
relevant pool (S5).

CZL 6–10 HAS NO CONTENT
The most psychologically sophisticated levels (7–10 in particular — "declare
your interest directly", "become the spectacle", "just outside acceptable") are
well-designed but have zero catalog entries. Users never experience them.

────────────────────────────────────────────────────────────────────────────────
10.3 THE WEEKLY STREAK — DESIGN ASSESSMENT
────────────────────────────────────────────────────────────────────────────────

The weekly streak design (kWeeklyXpThreshold = 300, Mon–Sun, freeze mechanic)
is sound. 300 Aura ≈ 4 easy or 1–2 hard challenges. Achievable without daily
commitment. Auto-freeze provides retroactive forgiveness on return. Pending
streak creates motivational urgency without penalty.

Remaining opportunity: connect weekly streak and weekly goal into one unified
system. Currently they run in parallel. "Your streak continues when you hit your
weekly goal" would simplify the mental model.
