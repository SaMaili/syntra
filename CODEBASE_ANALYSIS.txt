SECTION 1 — WHAT THE APP IS
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Syntra is an offline-first Flutter app for building social confidence through
deliberate social challenges. Users are presented with real-world social tasks
(e.g. "start a conversation with a stranger", "give someone a compliment"),
accept them with a countdown timer, and log whether they succeeded or not.
"Aura Points" (XP) is awarded on success, weekly streaks are tracked, and every
attempt is stored in a logbook.

The app is structured around a progression system: a five-level Comfort Zone
Level (CZL) which gates which challenges are visible, unlocking harder content
as the user completes enough challenges at their current level.

Each day a Mission Board offers three tailored challenges (Comfort / Growth /
Bold tier), with a 10% Aura bonus for completing daily missions. The app
reminds users via local notifications and celebrates streaks with an animated
screen.

There is no backend, no account system, and no cloud sync. All data lives on
the device.

TECH STACK:
  Flutter (Dart) · Riverpod 2.x · go_router · SQLite (sqflite) ·
  SharedPreferences · flutter_local_notifications · fl_chart ·
  audioplayers · vibration · intl (flutter_intl)

PLATFORM SUPPORT:
  Android — fully supported, including exact-alarm scheduling via AlarmManager
  iOS — supported with flutter_local_notifications (UNUserNotificationCenter);
        no native scheduling layer equivalent to Android exists yet

APP VERSION: 1.0.0+1 (pre-release)
DART SDK: ^3.8.1

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

─── 3.1 APP STARTUP ────────────────────────────────────────────────────────────

main() runs these steps synchronously before runApp():

  1. WidgetsFlutterBinding.ensureInitialized()
  2. tz.initializeTimeZones() — timezone data for notification scheduling
  3. _copyDatabaseIfNeeded() — copies challenge_database.db from assets to the
     sqflite directory as logbook.db if not already present (first launch only).
     This DB now only stores the logbook table; the challenge catalog is JSON.
  4. _migrateSettingsJson() — one-time migration: reads legacy settings.json
     from documents dir, writes values to SharedPreferences, deletes the file.
     Best-effort (errors ignored).
  5. SettingsRepository.instance.loadOnboardingComplete() — read before router
     init so the router can set initialLocation correctly.
  6. routerNotifier = RouterNotifier(onboardingDone) — ChangeNotifier for GoRouter.
  7. SyntraNotificationService.instance.initialize() — Flutter plugin init.
  8. runApp(ProviderScope(child: SyntraApp()))

SyntraApp (ConsumerWidget):
  - Watches themeModeProvider → ThemeMode (light/dark/system)
  - Watches localeProvider → Locale (en/de)
  - Renders MaterialApp.router with AppTheme.light(), AppTheme.dark(),
    appRouter (GoRouter), S.delegate for localization.


─── 3.2 NAVIGATION ─────────────────────────────────────────────────────────────

Router: go_router (GoRouter) with a ChangeNotifier-based refresh.

ROUTE GUARD (router.dart):
  GoRouter.redirect checks routerNotifier.onboardingComplete:
    - Not done + not on /onboarding → redirect to /onboarding
    - Done + on /onboarding → redirect to /
    - Otherwise → null (no redirect)

NAMED ROUTES (AppRoutes abstract class):
  /                    → HomeBar (bottom-nav shell)
  /onboarding          → OnboardingScreen
  /active_challenge    → ActiveChallengeScreen (extra: Challenge)
  /challenge_done      → ChallengeDoneScreen (extra: _ChallengeDoneArgs)
  /logbook             → LogbookPage
  /logbook_detail      → LogbookDetailPage (extra: Map<String,dynamic>)
  /about               → AboutNotePage
  /streak_celebration  → StreakCelebrationScreen (extra: _StreakCelebrationArgs)

EXTENSION HELPERS (AppNavigation on BuildContext):
  context.goActiveChallenge(challenge)
  context.goChallengeDone(challenge, rewardFactor)
  context.goLogbook()
  context.goLogbookDetail(entry)
  context.goAbout()
  context.goStreakCelebration(streak, isMilestone)
  context.pushPriming(challenge) → pushes PrimingScreen as overlay

BOTTOM NAVIGATION (HomeBar):
  Uses a PageView + NavigationBar. Tabs:
    0 — ChallengesScreen    (explore icon)
    1 — DailyChallengeScreen (calendar icon)
    2 — ProfileScreen        (bar_chart icon)
    3 — SettingsScreen       (settings icon)

  PageView is swipeable (BouncingScrollPhysics).
  Programmatic tab switches use homeTabIndexProvider (StateProvider<int>).
  HomeBar listens to homeTabIndexProvider and calls animateToPage().

  SCROLL-TO-TOP BEHAVIOR:
  Re-tapping the already-active tab fires the corresponding scroll-to-top
  provider (challengesScrollToTopProvider, dailyScrollToTopProvider,
  profileScrollToTopProvider, settingsScrollToTopProvider). Each screen
  listens via ref.listen and animates its ScrollController to offset 0.
  Guard: tap only fires scroll if !_isAnimating (prevents re-entrant trigger
  from the provider write that follows tab switches).

NOTEWORTHY INCONSISTENCY:
  ActiveChallengeScreen uses Navigator.of(context).push<double>() to reach
  ChallengeDoneScreen — not GoRouter. This is intentional (needs a return value)
  but means /challenge_done is not reachable via deep link from this path.


─── 3.3 CHALLENGE MODEL ────────────────────────────────────────────────────────

File: lib/challenge.dart

  Field              Type      Notes
  ─────────────────────────────────────────────────────────────────────────────
  id                 String    Sequential string ID, e.g. "0"–"111". From JSON.
  title              String    Localized title
  description        String    Main challenge text
  hints              List<String>  Suggested phrases shown in hint dialog
  level              int       1–10 explicit difficulty level from catalog
  xp                 int       Base reward points (called "Aura Points" in UI)
  time               int       Timer duration in seconds
  type               String    "solo" | "group" | "coop" | "dare"
  flirt              bool      Whether this is a flirt-type challenge
  environment        String    "all" | "street" | "transit" | "cafe" | "event"

All fields are final (immutable). The model is a pure data holder with a const
constructor. Challenge IDs are sequential 0–111 (112 challenges total). The
re-enumeration removed all gaps that existed in prior versions (was 0–181 with
70 gaps). IDs are synchronized across challenges.json, en.json, and de.json.


─── 3.4 CHALLENGE DATA LAYER ────────────────────────────────────────────────────

CATALOG (read-only, JSON):

  ChallengeRepository (lib/data/challenge_repository.dart)
  Pattern: Singleton, in-memory cache per language

  loadChallenges(languageCode) → Future<List<Challenge>>:
  1. Returns cached list if language matches.
  2. Loads assets/data/challenges.json (id, xp, timer, type, flirt, level, env).
  3. Loads assets/data/translations/{languageCode}.json (title, description, hints).
  4. Falls back to 'en' translations if a key is missing.
  5. Builds List<Challenge> and stores in _cache.

  invalidate() clears the cache (e.g., on language switch).

LOGBOOK (read/write, SQLite):

  LogbookRepository (lib/data/logbook_repository.dart)
  Pattern: Singleton, lazy database open

  Database: logbook.db (path via getDatabasesPath())
  Schema version: 2

  logbook table (current schema — all columns in CREATE TABLE):
    id               INTEGER PK AUTOINCREMENT
    challenge_id     TEXT     (sequential string ID, e.g. "42")
    status           TEXT     'success' | 'tried'
    earned           INTEGER  XP awarded (0 for aborted)
    timestamp        DATETIME ISO8601 string
    notes            TEXT     nullable
    feeling          INTEGER  nullable, 0–4 emoji scale
    perception       INTEGER  nullable, 0–4 emoji scale
    duration_seconds INTEGER  nullable
    pre_anxiety      INTEGER  nullable, 0–4 pre-challenge anxiety rating

  Migration history:
    v1 → v2: Added three indexes for query performance:
      idx_logbook_status_challenge ON logbook(status, challenge_id)
      idx_logbook_timestamp        ON logbook(timestamp)
      idx_logbook_challenge        ON logbook(challenge_id)

  Key methods:
    addEntry(...)                        → INSERT
    filteredEntries({limit, offset,      → paginated SELECT with optional
      status, challengeIds})               status + ID filter
    allEntries({limit, offset})          → paginated SELECT DESC
    entryById(id)                        → SELECT by PK
    overviewStats()                      → aggregate: totalXp, todayXp,
                                           completedAllTime, completedToday,
                                           weekStreak, pendingWeekStreak,
                                           minutesBrave
    weeklyXpByWeek({weeks=52})           → Map<isoWeekKey, xp> for streak logic
    currentWeekXp()                      → int XP earned this Mon–Sun week
    weeklyXp({days=7})                   → List<int> XP per day (oldest→newest)
    weeklyChallengeCounts({days=7})      → List<List<int>> [successes, tried] per day
    activityHeatmap({weeks=12})          → Map<dateStr, count>
    completedChallengeIds()              → Set<String> all success challenge_ids
    latestCompletionDates()              → Map<String, DateTime> newest per challenge
    lastNotesForChallenge(id)            → most recent notes
    deleteEntry(id)                      → DELETE
    challengesCompletedThisWeek()        → int (for weekly goal progress)
    moodHistoryForChallenge(id)          → List<int> feeling scores
    averageMoodPerDay({days=14})         → List<({DateTime date, double avg})>
    countStreak(dates, today) [static]   → legacy daily streak (test suite compat)

  WEEKLY STREAK ALGORITHM (lib/logic/weekly_streak_logic.dart):
    Pure, side-effect-free. Uses ISO 8601 week numbering (Mon-aligned).
    kWeeklyXpThreshold = 300 Aura — minimum weekly XP for a streak week.
    countStreak(): walks back from current week, counts consecutive qualifying
      weeks. The current in-progress week counts immediately once it hits 300.
    countPendingStreak(): starts from last week — shows streak-in-grey when
      the current week hasn't activated yet.
    countStreakAutoFreeze(): auto-applies available streak freeze charges to
      consecutive missed past weeks (identical to Duolingo's freeze mechanic).

─── 3.6 COMFORT ZONE LEVEL (CZL) SYSTEM ────────────────────────────────────────

File: lib/logic/comfort_zone_logic.dart

Five levels, each with a name and description:
  1 — Warming Up        "Micro-interactions — low stakes, high growth"
  2 — Breaking the Ice  "Brief exchanges with real humans"

─── 3.7 DAILY MISSIONS SYSTEM ──────────────────────────────────────────────────

File: lib/logic/daily_missions_logic.dart
Provider: DailyMissionsNotifier (AsyncNotifierProvider) in lib/providers/daily_providers.dart

Three tiers per day:
  Comfort — from the bottom third of the catalog by XP
  Growth  — from the middle third
  Bold    — from the top third

Selection algorithm (DailyMissionsLogic.getTodayMissions):
  1. Load full catalog for the current language.
  2. Filter out flirt challenges (preferred pool).
  3. Sort by XP, split into thirds.
  4. If stored date ≠ today OR any stored ID is null → re-roll all three.
  5. Randomly pick one challenge per tier, persist IDs + date.
  6. Return List<DailyMission> with completed flags from SharedPreferences.

markCompleted(tier) → sets the tier's done key to true.

XP BONUS: ChallengeDoneScreen adds a 10% bonus (rounded) to earned Aura Points
when isDailyMission = true and the challenge was not aborted.

─── 3.20 GAMIFICATION LOOP ─────────────────────────────────────────────────────

Full user loop:

  1. Onboarding → set CZL → unlock initial challenge pool
  2. Open app → see challenges filtered by CZL + applied filters
  3. Accept a challenge (or start a daily mission)
  4. Priming screen → motivational framing before the challenge
  5. Timer runs → go do it in the real world
  6. Return → mark result → complete survey (mood, perception, notes)
  7. Aura Points awarded → logged to SQLite → weekly XP accumulates
  8. Weekly XP ≥ 300 → current week "active" → weekly streak active
  9. Streak freezes auto-apply to missed past weeks (if freezes available)
  10. CZL completions++ → at 3 completions → level-up screen → new challenges unlocked
  11. Stats/Profile screen shows Aura charts, heatmap, badges, weekly goal
  12. Notifications remind user each day via configurable time slots

WEEKLY STREAK: A streak week requires earning ≥300 Aura (kWeeklyXpThreshold).
Consecutive qualifying weeks = weekly streak. The current in-progress week
activates the moment it hits the threshold. Streak freezes protect up to 2
missed past weeks from breaking the streak.

Sound effects (SoundService via audioplayers):
  playClick()    — nav bar taps
  playDing()     — challenge start
  playSuccess()  — challenge success
  playError()    — challenge abort/failure

Haptic feedback:
  HapticFeedback.selectionClick() on nav bar press
  VibrationService.start()        — when challenge timer starts
  VibrationService.timerWarning() — at 10 seconds remaining
  VibrationService.timerEnd()     — when timer hits zero
  VibrationService.success()      — on successful completion
  VibrationService.milestone()    — on streak milestone

Badges (lib/logic/badges_logic.dart):
  8 badges: first_step, ten_challenges, fifty_challenges,
  three_day_streak, seven_day_streak, century_xp, five_hundred_xp, brave_minutes.
  Each has id, IconData, Color, and a condition function.
  Evaluated from overviewStatsProvider + personalBestStreakProvider.

SECTION 10 — PSYCHOLOGICAL DESIGN ANALYSIS
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

This section evaluates what psychological mechanisms the app currently uses,
which ones work well, and which are missing or misused.

────────────────────────────────────────────────────────────────────────────────
10.1 WHAT THE APP GETS RIGHT
────────────────────────────────────────────────────────────────────────────────

GRADUATED EXPOSURE (STRONG)
The CZL system is a direct implementation of the clinical exposure therapy
concept: face the least anxiety-provoking situations first, then escalate as
you habituate. Level 1 ("Micro-interactions") → Level 5 ("The Bold Zone")
exactly mirrors a SUDS (Subjective Units of Distress) hierarchy used by
therapists treating social anxiety. This is the most psychologically credible
part of the app. The mechanism is sound.

BEHAVIORAL COMMITMENT (STRONG)
The 15-second abort lock on the active challenge screen is a well-designed
implementation of commitment theory. Removing the exit option briefly forces
the user to sit with discomfort rather than flee immediately. Research on
exposure therapy shows that brief tolerance of anxiety — not avoidance — is
what produces habituation. The lock is the right call.

PRIMING / IMPLEMENTATION INTENTIONS (GOOD)
The PrimingScreen gives users 5 seconds of contextual framing before the
timer starts (different headlines for flirt/group/quick/hard challenges).
This mirrors implementation intentions: "I am about to do X in situation Y."
The duration picker gives a small act of agency, reducing reactance.

IMMEDIATE REINFORCEMENT LOOP (STRONG)
Challenge → timer → done → XP count-up animation → coach message → survey.
The full loop is tight. The XP counter animation is a direct dopamine trigger.
Reinforcement is most effective when it arrives within seconds of the behavior.

WEEKLY STREAK DESIGN (MUCH IMPROVED)
The shift from daily to weekly streaks (kWeeklyXpThreshold = 300, Mon–Sun)
correctly addresses the mismatch between social challenges and daily habit apps.
Users can miss a day for work, travel, or low social energy without losing their
streak, as long as they hit 300 Aura across the week. The streak freeze mechanic
provides additional protection. This is now a well-designed retention system.

METACOGNITIVE MOOD TRACKING (GOOD BUT UNDERUSED)
The post-challenge survey captures feeling and perception per challenge.
This is metacognitive training — users become aware of how they felt, building
interoceptive awareness. Per-challenge mood history in ChallengeDetailScreen is
genuinely valuable. The data foundation is excellent.

────────────────────────────────────────────────────────────────────────────────
10.2 WHAT IS MISSING OR BROKEN
────────────────────────────────────────────────────────────────────────────────

THE PREDICTION-REALITY GAP (PARTIALLY IMPLEMENTED)
This is the single most evidence-backed mechanism for reducing social anxiety.
Research consistently shows that people with social anxiety catastrophically
over-predict how bad social situations will feel. Seeing the gap repeatedly —
expectation vs. reality — is what creates lasting change.

Current state:
  ✅ PrimingScreen has a 5-icon pre-challenge anxiety picker (1–5 scale,
     "How nervous are you?" with icons from very satisfied to very dissatisfied).
  ✅ pre_anxiety is passed to the challenge session and stored in logbook.pre_anxiety.
  ❌ The done screen does NOT yet show a comparison ("You expected 4/5 — reported 2/5").
  ❌ The logbook detail view does not surface the pre/post gap.

Remaining work: one targeted addition in ChallengeDoneScreen and LogbookDetailPage
to surface the gap. The data is already captured — only the display is missing.

NO INSIGHT LAYER ON THE LOGBOOK
The logbook stores rich data (mood, perception, notes, XP, duration, pre_anxiety)
but shows it only as a chronological list. Missing derived insights like:
  - "You complete 85% of solo challenges but only 40% of group ones"
  - "Your average mood after challenges is 3.8/5"
  - "You haven't tried a Bold challenge in 2 weeks"

ABORT IS FRAMED AS FAILURE, NOT AS ATTEMPT
Even an aborted challenge involved showing up, starting, and experiencing the
beginning of the situation. The app should frame aborts as "you tried, that
matters" more explicitly. Consider: rename "Tried" to "Attempted", celebrate
the attempt, and explain that partial exposure still reduces anxiety.

SOCIAL PROOF IS FAKE AND INERT
The "X others have done this challenge" (800–4499 deterministic hash) is not
doing real psychological work. Real anonymized user notes would be far more
anxiety-reducing. The UI slot is already there; this requires the backend (TODO H).

COACH MESSAGES ARE NOT CONTEXTUAL
7 generic messages hashed to a challenge ID. A coach message after a group
challenge should differ from one after a flirt challenge. Pool messages by
challenge type (solo/group/flirt/dare) and draw from the relevant pool.

NO REFLECTION PROMPTS IN NOTES FIELD
A blank text box produces less reflection than guided prompts. Add rotating
placeholder text: "What was easier than you expected?", "What would you do
differently?", "How did you feel physically?" Costs near-zero to implement.

────────────────────────────────────────────────────────────────────────────────
10.3 THE WEEKLY STREAK — DESIGN ASSESSMENT (UPDATED)
────────────────────────────────────────────────────────────────────────────────

The weekly streak design (kWeeklyXpThreshold = 300, Mon–Sun week, freeze mechanic)
is a significant improvement over the prior daily streak model. The key design
choices are sound:

  - 300 Aura ≈ 4 easy challenges or 1 hard challenge. Achievable in a realistic
    week without requiring daily behavior.
  - Freeze mechanic (up to 2 weeks) provides resilience for real-life disruptions.
  - Pending streak (grey display when current week is below threshold) gives
    motivational urgency without penalty — the streak "breathes" as you progress.
  - Auto-freeze applies retroactively on the next successful session, so a user
    who was sick and comes back still gets credit for their frozen week.

Remaining improvement opportunity:
  - Connect the weekly streak to the weekly goal card so they tell a unified story.
    Currently weekStreak and weeklyGoal are parallel systems. Consider:
    "Your streak continues when you hit your weekly goal."
  - Show a "X days left in your streak week" countdown to create appropriate urgency.

     screen will never know they earned it. Confirm that badge_unlocked_screen.dart
     is triggered from ChallengeDoneScreen after XP animation.
